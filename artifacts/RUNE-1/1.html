Confirmed by code recon: preprocessed has the same pixel dimensions as capturedBitmap — both allocated from source.Width/source.Height. Row rects derived from the preprocessed pass index straight into the raw frame with no coordinate remapping. The only upscale in the pipeline (UpscaleForOcr, ×3) happens after row detection, per-row, for Tesseract only.
Resolution risk is two-layered, not one fraction. The capture region is chosen in absolute pixels per profile (interpolated for unlisted resolutions), then PanelLeftFraction cuts a fraction of that. Spike check (a) must be run per profile, not reasoned about once.

Identity key — both halves required

shape — greyscale dHash (64-bit)Hand-rolled, ~40 lines, no new dependency. Computed on the 32×32 normalised cell.
hue — dominant hue bucketCarries tier / sub-tier colour (blue / purple / gold glyphs), which the preprocessed image cannot.
Settled, do not re-open. Whether the same glyph shape can roll at different tiers is an unresolved game-mechanics question. The composite key is deliberately more general so that question cannot block implementation — if weight turns out to be pure shape, the hue component is constant per shape and harmless.

Spike gate — must pass before implementation continues

CheckQuestionPass barNeeds game art?
(a)Does the icon strip fall inside the capture region at all 5 profiles? Strip has positive width and each of the 5 cells is ≥24×24 raw px, at every profile No — pure arithmetic over OcrResolutionProfiles × PanelLeftFraction
(b)Are gilded borders separable from non-gilded in the raw frame, across tier colours? Zero overlap between class distributions over ≥30 samples per class, ≥3 tier colours, ≥2 profiles Yes — real captures required
(c)Is the dHash stable frame-to-frame, and across profiles after normalisation? Same sprite/profile Hamming ≤2; cross-profile ≤4; two different glyphs ≥10 Yes — real captures required
The harness named in the original ticket does not exist. tests/OcrPricingSimulator/ is a text-only pricing tool — it parses item-name strings and hits pricing APIs. It contains zero image or Bitmap code and cannot feed a PNG through the league-window reader. No offline image harness exists anywhere in the repo, and no OCR fixture PNGs are checked in. Building that harness is step 1 of this card, not an assumed starting point.
The ≥10 cross-shape bound is not optional. Without it, "stable" is trivially satisfiable by a degenerate hash that returns the same value for every glyph.

Fail-soft contract

SituationBehaviourWhy
Row yields a cell count ≠ 5Skip row, log, never throw One mis-segmented row must not take down the OCR pass that the existing price path depends on.
Border metric lands in the ambiguous bandTreat as non-gilded, drop, log A wrong key corrupts Card B's "already carrying" set and gives actively wrong advice; a missing key only under-reports one row. Bias toward omission, never toward guessing.

If the spike fails

Report and stop — do not work around it. Widening the capture region to rescue check (a) would affect the existing price OCR path and is out of scope for this card. If (b) or (c) fails, Card B should not be built as designed, and that finding is the deliverable.
