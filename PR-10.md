Rune tracker UX. Needs no new captures and no sprite names, so it could proceed while both of those are outstanding.

## What was wrong

- **No sense of progress toward "set and forget."** Naming sprites is a one-off chore, and nothing said how much was left — 34 rows look identical whether 0 or 30 are bound.
- **All 34 rows, always**, inside an already-scrolling settings pane in a window that can be 500px wide.
- **The carried set was invisible.** It is the tracker's actual state, and reading it meant scanning 34 checkboxes.
- **No bulk escape from junk sprites.** A run of misread cells fills the store to `MaxUnboundBindings`, after which new sprites are silently dropped — and the only way out was one "Forget" at a time.

## Changes

- `RuneLibrarySummary.Describe` → `"9 of 34 bound · 3 carried this run"`. A sighting deliberately does not count as progress: an unnamed sprite still needs the user.
- `RuneLibraryFilter` (All / Not seen yet / Seen / Carried) applied over a full backing list, so switching filters never loses in-flight edits. Each filter names its own empty state.
- Carried strip: dismissible chips above the rows, hidden when empty, refreshed on toggle rather than waiting out the presenter's 250ms debounce.
- `RuneCatalog.ForgetAllUnbound()` + a "Forget all" button. Clears pending first sightings too — otherwise the junk returns on its next sighting and the button would not stick.

Filtering and summarising are pure helpers, so they test without a WPF dispatcher.

## Note on the tests

The first draft of the catalog test failed for a real reason worth recording: `0x1111` and `0x2222` are 8 bits apart, inside `MatchHammingThreshold`, so the matcher folded three "distinct" sprites into one binding. The fixtures now use hashes 32+ bits apart, with a comment saying why.
