Fixes the user's report of **57 unbound sprites in a 34-rune game**.

## Cause

The identity crop was not anchored to the rune. `AssignLatticeGlyphBounds` derived it from the *surroundings*:

```
right = prevPlain.Bounds.Right + pitch * slotsAway   // neighbour's border + integer-divided median pitch
glyph = new Rectangle(right - rowHeight, rowTop, rowHeight, rowHeight)   // rowTop/rowHeight from OCR
```

Every input there can land a pixel off between frames.

## Measurement

`RuneCropStabilityDiagnostics` shifts the crop and re-hashes, on the real fixture:

```
                worst +/-1px   worst +/-2px
lattice (old)      26 bits        39 bits
plate   (new)       0 bits         0 bits
```

`MatchHammingThreshold` is 8; the fixture's own `DifferentRuneMinHamming` is 16. **One pixel of drift exceeded both** — the same rune re-hashed into something the matcher read as a *different* rune. That is the 57.

The new crop is bit-identical across the entire ±2px grid.

## The fix

`FindPlateBounds` locates the dark plate inside the gold frame. That edge belongs to this cell and nothing else, so the crop stops depending on neighbours, pitch arithmetic and OCR row geometry.

Two things the fixture forced, both documented at the call site:

- **Only the sides and bottom of the frame are inside the detected cell.** The row extent clips the top — it reads 38-42% gold where the bottom reads 77-96%, and one row has no top gold at all. The plate is square, so a missing edge is derived from the width rather than failing the cell.
- **Scanning runs outside-in, never centre-out**, or a rune with a yellow glyph would stop the scan on its own artwork. When the frame is not inside the box at all (row 4's cell is 51px where its neighbours are 52), the scan looks a bounded distance outside — not far enough to reach the next cell.

Falls back to the lattice box when no plate is readable, so a marginal cell degrades instead of disappearing.

## Migration

Every stored hash is now stale. The user layer carries a `hashVersion` and drops bindings from an older generation on load.

This is not cosmetic: without it, 57 dead bindings would sit at the 64 `MaxUnboundBindings` cap and no new sprite could ever be stored — the feature would appear dead in the new build. Weights and rune-level carried flags survive the drop.

## Follow-on

Auto-matching sprites against the poe2db reference icons was rejected earlier on evidence gathered with this unstable hash, so that rejection is no longer sound and is worth re-testing.
